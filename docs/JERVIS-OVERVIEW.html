Jervis
AI Production Assistant

Ask a production question in plain language. Get one consolidated answer drawn from the systems the plant already runs, with every number attributed to the system it came from.

React front end · Node back end · 78 automated server tests · runs fully offline on synthetic data

The problem

Production answers live in five systems and nobody has time to visit all of them

Today

  • Issue history sits in Databricks, KPIs in Power BI, maintenance in the Integral Portal, machine state in MQTT.
  • A simple question such as "what went wrong on Friday?" means four logins and a spreadsheet.
  • Managers get summaries late, and the numbers rarely agree.

What Jervis does

  • Understands the question, decides which systems to read, retrieves, combines, answers.
  • Headline, short narrative, KPI tiles, charts, tables, links back to the owning dashboard.
  • Hands-free by voice or typed, with a stage-by-stage trace on every answer.

How an answer is built

Five stages, every one visible in the trace

1 · UnderstandIntent plus entities: period, shift, line, model, error code, part, checkpoint, cost centre, severity.
2 · PlanAn explicit intent-to-retrieval plan. No model improvisation, reviewable per question.
3 · RetrieveIssue history, Power BI measures, Integral Portal tickets, MQTT downtime signals.
4 · CombineOrchestrator merges results and records which system supplied which fact.
5 · AnswerHeadline, narrative, KPI tiles, charts, tables, deep links. Spoken form for voice.

Numbers never come from the language model. Optional Claude narration rewrites the wording only, and falls back to deterministic text on any failure.

Example

"What problems did we have on Friday?"

You:     "Hey Jervis"
Jervis:  "Good morning, sir! What would you like to know?"
You:     "What problems did we have on Friday?"
Jervis:  "52 problems recorded on Friday 2026-10-02.
          There were 52 issue events affecting 45
          vehicles..."
Jervis:  "Anything else?"
You:     "Which models were affected?"   (no wake phrase)

Hands-free voice

A conversation, not a series of commands

Wake and greet

Wake phrase "Hey Jervis", plus the mis-hearings speech recognition actually produces. A time-of-day greeting is spoken before anything is retrieved.

Ask in one breath

"Hey Jervis, what problems did we have on Friday?" skips the greeting and answers straight away. A button covers noisy lines.

Follow-ups

No wake phrase needed for 9 seconds after an answer. Context carries across turns.

Spoken answers

A shorter form of the same facts. "64 h 43 min" becomes "64 hours 43 minutes"; error codes are read digit by digit.

Private by design

Browser Web Speech API in Chrome or Edge. No audio leaves the machine. Firefox falls back to text.

Configurable

Wake phrase, greeting, prompts and timings come from one endpoint, so wording changes without a front-end release.

Security and access

Real sessions, server-enforced roles, audit on every question

Authentication

  • Server-side session, opaque httpOnly cookie
  • scrypt-hashed passwords
  • Login rate-limited per address
  • Deny by default on every protected route and AI tool

Authorisation

  • Three roles: production manager, quality engineer, line viewer
  • Cost figures, audit trail and integrations gated by permission
  • One user cannot read another's conversation

Data handling

  • Retrieval-time redaction by role
  • Per-question audit row: role, systems read, redactions
  • No Mercedes data anywhere. Fully synthetic, fixed seed, identical on every boot

Architecture

One data contract, so the real warehouse is a single adapter

server/src/
  agent/        nlu . planner . tools . orchestrator
                synthesizer . llm . greeting
  connectors/   Databricks . Power BI . Integral . MQTT
  data/         repository contract + adapters
                (memory . postgres . databricks)
  auth/         users . sessions . cookies
  security/     roles . redaction . audit
  integrations/ definitions . store . probe
  routes/       auth . chat . summaries . system
                dashboard . issues . analytics
                conversations . integrations . voice
web/src/
  pages/        14 pages
  components/   voice loop . answer card . charts
db/schema.sql   target schema (production . maintenance
                . telemetry . audit)

Repository contract

Eight methods: meta, listIssues, countIssues, aggregateIssues, vehicleImpact, listMaintenance, listDowntime, dailyTrend. One filter object shared by all of them.

Nothing above the contract knows where data comes from. Switch with JERVIS_DATA_SOURCE=memory | postgres | databricks.

Stack: React 18, Vite, Tailwind, Radix UI, Recharts, React Query · Express 4, Node 20+, Anthropic SDK.

Requirements coverage

Built · stood in for · deliberately open

built

  • Natural-language understanding and explicit planning (§4.1)
  • All ten example questions (§4.2)
  • Daily and shift summaries over the three shifts (§5)
  • Power BI lookup and deep links (§6)
  • Cross-system workflow (§8, §9)
  • Voice and text (§11)
  • Sign-in, roles, redaction, audit (§12)
  • Source citations on every answer (§17)

stood in for

  • Databricks, Power BI, Integral Portal, MQTT run on synthetic data until credentials are supplied and enabled
  • Identity source is a seeded user store; swap for SSO / Entra ID
  • Narration is deterministic by default; Claude rewording is optional

open

  • Extend, reuse or wrap the existing chatbot (§10)
  • Final LLM / RAG architecture
  • Database and hosting architecture
  • Authorisation model and real roles
  • Final supported question set
  • Performance, SLA, retention, monitoring
